> 审查对象：`BromyuMusicNext/quemusicproject`（Qt 6 / QML + C++ 桌面音乐播放器）
> 审查方式：确定性 lint（qt_review_lint.py / qt_qml_lint.py）+ 12 路深度分析代理（C++ ×6、QML ×6）+ JS AOT 编译专项 ×1，其中 3 路 QML 代理因 API 限流改由主代理检索补齐

## 2. C++ 层问题

### 2.1 安全漏洞（最高优先级）

**[S1] 酷狗 token 随明文 HTTP 外发** · `api/KugouApi.cpp:409` + `api/ApiHttp.h:29-30` · 置信 92
`ApiHttp::get()` 无条件对任意 URL 设置 `Cookie` 头；登录后 `MusicApiService.cpp:342` 把含 `token=...` 的 cookie 注入 `m_cookie`，随后所有 `http://` 端点（mobilecdn / msearch / lyrics.kugou.com）都携带账号凭证，MITM 可直接窃取。
→ **缓解**：全部酷狗端点改 https；`ApiHttp` 对非 https URL 强制剥离 `Cookie` 头。

**[S2] 账号凭据明文落盘于 exe 旁 `Account.ini`** · `cpp/AccountManager.cpp:46, 796-818, 184` · 置信 90
`m_configPath = applicationDirPath() + "/Account.ini"`，明文写入网易云完整登录 Cookie（含 `MUSIC_U`）、`anonymousToken`、酷狗 `token; userid`。程序目录通常对本机所有用户可读，便携盘拷贝即带走全部会话——与 WebDAV 密码用 DPAPI 的做法自相矛盾。
→ **缓解**：迁移到 `QStandardPaths::AppDataLocation`，复用 `WebDavStore` 的 DPAPI 封装。

**[S3] 下载文件名来自远端元数据，无清洗（路径穿越）** · `cpp/DownloadManager.cpp:208` · 置信 85
`s.value("name") + ".mp3"` / Kugou 的 `fileName` / B 站 `title + ".m4a"` 直接拼 `downloadDir + "/" + task.fileName`。含 `../`、`/`、`:` 即可越出下载目录写文件；配合 [S1] 的明文链路可被定向利用。
→ **缓解**：`addDownload` 入口统一 `QFileInfo(name).fileName()` + 剔除 `\\/:*?"<>|` 与控制字符。

**[S4] 非 Windows 平台 WebDAV 密码等价明文（Base64）** · `cpp/webdav/WebDavStore.cpp:53-62` · 置信 88
`#else` 分支 `encryptText` 就是 `toBase64()`；且 Windows 分支 `CryptProtectData` 失败时静默返回空串却被当作有效密码存入。
→ **缓解**：macOS/Linux 接 Keychain / libsecret；加密失败必须报错回滚。

**[S5] 允许显式 `http://` 的 WebDAV 服务器，Basic 凭据全程明文** · `WebDavStore.cpp:72-82` + `WebDavClient.cpp:93` + `WebDavCache.cpp:150` + `FfmpegDecoder.cpp:103` · 置信 85
`normalizeUrl` 只在缺 scheme 时补 https，用户显式写 `http://` 被原样保留；`user:password` 的 Base64 随每次 PROPFIND、缓存下载发送，甚至通过 `av_dict_set("headers", …)` 交给 FFmpeg 的 HTTP 客户端。
→ **缓解**：含凭据的请求强制 https（拒绝或显著警告）。

**[S6] 播放地址回退构造 `http://` 外链，音频明文传输** · `api/NeteaseCloudApi.cpp:374-377` · 置信 80
`http://music.163.com/song/media/outer/url?id=...` 直接交给 DownloadManager / FFmpeg 拉流，MITM 可替换音频内容（恶意媒体文件随即进入 FFmpeg 解码 + TagLib 解析）。该外链 https 可用。
→ **缓解**：改 `https://`。

**[S7] 日志输出含 token 的完整 URL** · `api/ApiHttp.h:36` + `KugouApi.cpp:1289` · 置信 78
请求失败时 `qWarning() << reply->url().toString()` 会打印查询串，而 `requestSignedPlayInfo` 把 `token`、`userid` 放在查询串中，失败即落盘到 LogManager 日志。
→ **缓解**：日志只记 `scheme://host/path`，或对 `token=` 脱敏。

**[S8] 插件系统无安全边界** · `cpp/plugins/PluginStore.cpp:29-30, 103-106, 143-162` · 置信 78
扫描 `applicationDirPath()/plugins/`，任何能写该目录的进程都能植入插件；`info.json` 的 `entry` 经 `absoluteFilePath()` 解析未限制 `../` 越界；`install()` 无签名/哈希校验。QML 加载后拥有与主程序相同的 Qt 对象（网络、文件、context property）。
→ **缓解**：加载前做规范化路径越界校验；安装包做哈希白名单；第三方插件用受限 QML 上下文加载。

**[S9] WebDAV 凭据前缀匹配过宽** · `WebDavStore.cpp:192-201` · 置信 72
`url.startsWith(root)` 纯字符串比较：`https://example.com/dav` 的凭据会匹配到 `https://example.com/dav-attacker/...`。
→ **缓解**：按 `QUrl` 解析后逐段比较 host+path，或给 `root` 补尾 `/`。

> 已核查**无问题**：全 `cpp/` 的 SQL 均为 `prepare + :绑定`（`DbService` 的 `.arg(table)` 只来自内部常量）；`FfmpegDecoder` 缓冲区长度受 `m_stageFrames - m_stageOffset` 约束无越界；`gpuRenderMode` 越界值安全落入空分支；`qrcode.js` 无 eval/远程脚本。

### 2.2 线程安全

**[T1] 音频缓冲重建是"超时放弃"而非真握手（可致堆越界）** · `cpp/audio/AudioEngine.cpp:226-246` · 置信 78
`m_audioFrozen` 置位后仅轮询 `m_decodeParked` 最多 200×1ms，超时后 GUI 线程照常让输出线程 `ring.configure()`（`m_data.assign` 可能重分配、改写非原子 `m_capacity/m_channels`）。若解码线程正阻塞在 `m_decoder.open()`（网络源可数十秒）未观测到标志，返回后会继续 `ring.clear()` + `ring.write()`，与 configure 无锁并发读写同一 `AudioRing` → 按旧容量 memcpy 越界写坏堆。
→ **缓解**：改条件变量/`QSemaphore` 真握手；解码线程确认停靠前 configure 不得返回，超时应放弃本次重建。

**[T2] `m_neteaseAnonymousToken`（QString）跨线程无锁读写** · `cpp/AccountManager.cpp:181, 145-146, 295` · 置信 75
池线程直接赋值，GUI 线程 `mergeNeteaseIdentity` 与另一池线程（验证码登录）并发读同一 QString——隐式共享 d 指针引用计数跨线程无锁更新是 UB。
→ **缓解**：池线程只算结果，经 `QMetaObject::invokeMethod(this, …, QueuedConnection)` 回主线程写成员（项目其他处已用此模式）。

**[T3] `LocalMusicScanner::startScan` 在 GUI 线程裸写 worker 参数** · `cpp/LocalMusicScanner.cpp:360-364` · 置信 70
`folder`/`nameFilters`/`sortField` 等被 GUI 直接写，而上一轮 `run()`（cancel 只在检查点生效）可能仍在读它们；`invokeMethod` 只保证新 run 排队，不保证旧 run 返回。QString/QStringList 跨线程无锁赋值（COW 引用计数撕裂）可崩溃。
→ **缓解**：参数打包为值对象随 `run` 一起投递。

**[T4] 环形缓冲游标 `std::atomic<int>` 长期溢出** · `cpp/audio/AudioRing.h:74-75` · 置信 63
48kHz×2ch 下每秒推进 96000，单世代连续播放约 **6.2 小时**后 `t + n` 溢出 `INT_MAX`（有符号 UB），`t % m_capacity` 错乱、读写索引失控。触发场景：直播流/长篇有声书不切歌。
→ **缓解**：改 `std::atomic<uint64_t>`（取模自动正确）。

**[T5] `m_sink` 裸指针跨线程读写（TOCTOU）** · `AudioEngine.cpp:311, 325, 333, 405` · 置信 62
输出线程在 `invokeOnOutput` lambda 内 new/delete，GUI 线程在 `startSink/stopSink/pause/outputFormatName` 中判空读取。
→ **缓解**：判空全部移入 lambda 内，或改 `std::atomic<QAudioSink*>`。

**[T6] `GetWave::m_enabled` 非原子 bool 跨线程** · `cpp/GetWave.cpp:108`（`.h:93`） · 置信 62
音频回调线程读、GUI 线程写。
→ **缓解**：`std::atomic<bool>`。

**[T7] 多个 QtConcurrent 任务并发进入同一 `ApiHelper`** · `cpp/AccountManager.cpp:56, 236, 275, 387, 493` · 置信 60
`ApiHelper::invoke` 以 `DirectConnection` 在调用者线程执行，仅 cookie 段有锁，方法体与 `set_cookie` 外部调用无锁；匿名注册 + 验证码 + 扫码轮询可同时进入。
→ **缓解**：为全部外部调用点加同一互斥量，或统一排队到专属线程。

### 2.4 模型契约

**[M1] `DownloadManager` 的 `FilePathRole` 从未通知** · `cpp/DownloadManager.cpp:199-219` · 置信 85
`task.filePath = savePath`（219 行）发生在 `emit dataChanged(mi, mi, {StatusRole})`（199 行）之后，且后续 `onFinished/onDownloadProgress/onErrorOccurred` 都不含 `FilePathRole`，而 `roleNames()` 注册了 `"filePath"` → QML 读到旧值（首次为空）。
→ **缓解**：先赋值再发信号，或补发 `{FilePathRole}`。

**[M2] `OnlineListModel::remove(index, count)` 未校验 `count <= 0`** · `api/OnlineListModel.cpp:100-109` · 置信 72
`count == 0` 时算出 `end = index - 1 < index`，向 `beginRemoveRows` 传非法区间（Qt 断言/视图状态破坏）。该方法为 `Q_INVOKABLE`，QML 可直接传 0。对照 `QueueModel::remove`（`QueueModel.cpp:112`）有完整守卫。
→ **缓解**：开头 `if (count <= 0) return;`。

**[M3] 三处 `rowCount()` 用 `Q_UNUSED(parent)` 忽略 parent** · `OnlineListModel.cpp:28`、`DownloadedMusicModel.cpp:93`、`DownloadManager.cpp:45` · 置信 70
`parent` 有效时仍返回行数，违反列表模型契约（应返回 0），挂代理/树形遍历时行为异常。同项目 `QueueModel.cpp:15`、`Favorites.cpp:42` 写法正确。

## 3. QML / JavaScript 层问题

### 3.1 JS AOT 编译专项（用户重点关注项）

#### 3.1.1 首先澄清一个关键事实：开源 Qt 无法把 JS 编译成 C++

- 真正把 JS 编译为 C++ 的是 **qmlsc，它是 Qt 商业版独占组件**（`cmake/qmltc.cmake:8` 已实测记录"本机 bin 下无 qmlsc.exe"）。
- 开源版可用的 AOT 只有两条：
  1. **qmlcachegen**（`qt_add_qml_module` 默认启用）——把 QML/JS 编译为 **V4 字节码**，消除解析开销，但函数仍在 V4 中执行；
  2. **qmltc**——只编译 QML **文档结构**为 C++，**不编译 JS**；本项目已备开关但默认 OFF。
- 因此当前可行目标是：**① 确保 qmlcachegen 不因错误静默回退为源码解释；② 让绑定/函数进入"可字节码预编译 + 编译期链接"的最优路径；③ 为将来若购入商业版 qmlsc 铺平 ~90% 的路。**

### 8.6 收藏写库失败：结论是环境，不是代码

用日志把链路钉死后得到的事实：

```
[favorites] 未知的收藏类型: "song"          ← refreshModel 的 SELECT 也失败了，读都没成功
[收藏] 写库失败 id="b35…" 原因="attempt to write a readonly database 无法获取行"
       库="C:/Users/Administrator/AppData/Roaming/BroNekoX/QueMusic/player_data.db"
```

**关键对照实验**（同一个 Qt 二进制，在四个位置各建一个全新 SQLite 库）：

| 位置 | 结果 |
|---|---|
| `Desktop\…\quemusicproject\.tmp-probe\scratch\fresh.db` | 建库 + 建表**成功** |
| `%APPDATA%\BroNekoX\qmdir\fresh.db` | 连文件都建不出来（`unable to open database file`） |
| `%LOCALAPPDATA%\BroNekoX\qmdir\fresh.db` | 同上 |
| `%APPDATA%\…\QueMusic\player_data.db` | 能打开，`CREATE TABLE`/`INSERT` 全部返回 `SQLITE_READONLY` |

即：**Qt 进程在 AppData 下没有 SQLite 写权限**，而同一时刻 Python、.NET `File.WriteAllText`、Win32 `CreateFileW` 在同一个目录里都能正常写；文件没有被独占（`File::Open` 以 `ReadWrite/None` 成功）；ACL 是 `Administrator: FullControl`；`PRAGMA journal_mode` 改成 `DELETE` 也不解决。所以这不是收藏的代码逻辑问题，而是 SQLite 层在这个路径上拿不到写能力（杀软的 SQLite 写入防护、或该目录被安全策略接管，是最常见的两种）。

**已在代码层面做的（不依赖环境就能验证的部分）**：

| 改动 | 作用 |
|---|---|
| `FavoritesModel::addFavorite/removeFavorite` 失败时 `qWarning` 打出真实原因 + 库路径，并 `emit errorOccurred` | 失败不再静默 |
| `QListView::toggleFavorite` 删掉无条件的「已收藏」提示 | 以前写库失败也弹成功，是**代码 bug**；现在成功/失败都由模型回执 |
| `DbService::markWriteFailed()` + `drain()` 里重开连接并重试整个任务 | SQLite 的 readonly 是连接级粘性状态，不重开的话后续所有收藏/歌单写会一直失败 |
| `DbService::open()` 用 `CREATE TABLE IF NOT EXISTS` 探一次写能力 | 开机就在日志里说清「库不可写」，不必等用户点收藏才发现 |

**排查工具**：`doc/qm-dbcheck.bat`（双击运行，结果写到桌面 `qm-dbcheck.txt`），会顺带删掉残留的 `-wal`/`-shm` 并验证目录写权限。

**下一步建议**（按代价从低到高）：① 退出 360 等安全软件后重试；② 右击程序选「以管理员身份运行」；③ 清掉 `-wal`/`-shm`；④ 若都不行，把库迁到程序自身目录（`QStandardPaths::AppLocalDataLocation` 之外的位置）。
